# v0.5.9：WSL 声明审查拆层

日期：2026-11-25（Asia/Shanghai）

## 起因

0.29.1 被拒，原因不是版本号不在名单，而是整个声明 patch 的摘要和钉住的 0.29.0 不一致。核对后发现差异只有三类：配置布尔值、预设里新增一个 DSH 自带工具行、新增一个 `!!js` 表达式。

旧做法的代价是：只要 WSL 调一个默认值，就要回来改一次摘要——等于按版本维护，和“不写死版本对”的初衷冲突。

## 做了什么

把“声明”拆成三层，各按各的规则：

1. **结构层（钉死）**：插入行的 id/名称集合、核心覆盖项（含 `disabled` 语义），顺序无关，摘要 `e820e82c…`。改动 → `wsl-structure-changed`。
2. **代码层（按表达式审查）**：每个 `!!js` 表达式取 sha256，只接受已登记集合
   - `75439e47…`：`!ctx.get('profileContext')`
   - `1850a687…`：预设技能目录（`@deepseek-ai/dsh-agent-preset` 包内 `skills`）
   出现未登记表达式 → `wsl-declaration-review-required`，摘要随错误带出。
3. **数据层（放行 + 展示）**：配置标量随便改；面板列出与 0.29.0 基线的差异（changed / added / removed 的项 id）。
4. **模块来源**：预设内只允许 `dsh-plugin-wsl-env*`、`@deepseek-ai/*`、`cordis:*`；其余 → `wsl-foreign-preset-module`。
5. 旧版本（0.24.0 / 0.26.2 / 0.28.0）走原有归档哈希路径，不套新门槛。

面板同时修掉 0.5.8 的显示问题：新增「新版声明待审查」短状态，与「本地安装」「已是最新」区分；行内「详情」显示声明差异与未审查表达式数量。

## 结果

- 0.29.0 与 0.29.1 结构摘要一致；`tool-office` 属官方包、`interrupt` 属数据、唯一新增表达式已审查 → **0.29.1 进入可更新**。
- 以后同结构、复用已审查表达式的新版本会自动通过；只有结构变化或新表达式才需要一次人工审查。

## 验证

- 完整回归：**411 项通过、0 失败、0 跳过**（串行）。
- 新增/改写测试：配置数据变化被接受；`!!js` 新表达式被拒且带摘要；外来预设模块被拒；结构摘要与 `WSL_STRUCTURE_CONTRACT` 一致；旧版本豁免新门槛。
- 真实归档对照：脚本 `compute-wsl-contract` / `compute-wsl-structure` 从公开 npm 归档计算两版摘要（只读，不入包）。
