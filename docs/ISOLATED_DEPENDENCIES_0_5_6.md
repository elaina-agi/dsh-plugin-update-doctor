# 纯 JS 依赖插件：结构化隔离更新（自 v0.5.6）

> **0.6.0 起**：本页描述的“宿主声明或依赖声明变化一律拒绝”已放宽。代际从新版本自身声明生成，装后核验；依赖范围变化只要已核验闭包满足就复用现有副本，否则报 `dependency-closure-requires-download`。下方内容保留为 0.5.6 阶段的设计记录。

## 解决什么问题

有些插件包本身没有问题，但**在已运行的 DSH 进程里卸载再安装新版会加载失败**：新旧版本共用同一解析路径，新代码可能沿用旧依赖的模块/解析缓存。原版 DSH rc.5 的官方常规热更新对这类插件会失败，官方自动恢复也常常不能把旧版重新加载起来。

v0.5.6 把这作为**一类插件的结构问题**处理，而不是逐个版本号修复。

## 准入依据

路线由**已安装包的真实结构**选定，不看保存的版本名单：

1. **路线选择**：已知存在该热更新失败的包（Union Search），或已安装包声明了受审查的纯 JS HTML 依赖闭包（`cheerio`、`turndown`、`@joplin/turndown-plugin-gfm`）。
2. **目标原包检查**：公开 npm 原包、SRI、包名与精确版本；`type: module`、单一静态入口、受控导出、无 `imports`／`bin`／`workspaces`、无可选依赖、无原生模块、无安装生命周期脚本。
3. **宿主声明不变**：旧、新原包的行、导出、`main`、`icon`、`dsh` 声明、peer 名称/范围、平台声明和固定插件行必须一致。插件行只允许单个静态 `insert` 行；动态表达式、`!!js`、include/extends 和覆盖已有行仍拒绝。
4. **依赖声明一致**：按范围比较声明，不因版本号变化放行不同依赖图。
5. **依赖闭包可核验**：每个物理副本都与公开 npm 原包逐字节比对；深层重复版本、循环、超限、链接、原生文件都拒绝。
6. **安装身份一致**：已安装文件必须与旧公开原包逐字节相同，Host 行状态符合预期。

不满足时给出具体原因（声明变化、依赖不可核验、数量超限等），不是笼统的“未验证这个版本”。

## 执行与完成条件

- 一次性生成**目标**与**不同 token 的旧版恢复**两个代际归档，保留旧根资源与前代路径；原始 JS 与资源字节不改，只把入口路由到全新路径。
- 官方管理器 `removeBundle` + `installBundle`（本地归档），宿主框架实例共享，不复制宿主依赖。
- **完成条件是四者同时成立**：官方 applied、当前安装字节与暂存一致、Host 行激活、Loader 实际运行的是新路径模块（精确 namespace 比对）。仅“包命令退出 0”不算成功。
- 目标失败时清理外部目标并用恢复归档重装；恢复也分别判断字节和运行状态，失败如实记录。
- 未知结果不重发；保留旧代上限耗尽时提前拒绝，不静默删除。

## 代价与边界

- 安装来源变为更新器管理的本地归档，**不再保留 npm 安装身份与内置 Versions 资格**，需要单独确认。
- 宿主声明或依赖声明变化的一律拒绝，需要新的审查；这条路线不承诺“所有版本永远能升”。
- 依赖闭包按文件逐字节核验，速度受网络与包体积影响。
- 验证范围见[验证记录](<VERIFICATION.md>)。隔离实验不等于每台设备、全部插件或全部浏览器交互均已验收。

## 与历史版本的关系

- 0.5.1 只做风险拦截，不算修复。
- 0.5.2 起提供代际归档机制，但准入写死 `0.10.24 → 0.10.25` 一对版本。
- 0.5.6 保留机制，把准入改为结构化证据；旧的 schema 1 代际记录仍可读取升级，新记录写 schema 2 并绑定宿主声明摘要。
