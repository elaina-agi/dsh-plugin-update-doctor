# v0.6.15：一键更新别再查第二遍

你问「一键更新选中的，还有个检查？很慢」。那确实是一次重复的检查，已经去掉。

## 那一次检查在做什么

点「一键更新选中」时，面板会先做一次**准备**再弹确认框。旧实现里这一步会**再跑一遍完整检查**：重新查版本、重新下载新旧两个归档、重新解析、重新走依赖图和已安装文件比对。而这些你刚在「检查全部更新」里已经让它做过一遍了。

所以 5 个插件时，光是弹确认框就等了约 13 秒（每次 2.6 秒，串行）。

## 本版改动

- **复用刚完成的检查**：2 分钟内、且覆盖全部已选项的检查结果直接用于准备。准备阶段仍然逐个包重新查一次元数据（网络断了照样报可重试的失败）、重新落盘两代归档、逐字节比对摘要——省掉的是重复的那一遍下载和预检，不是核验。
- **准备阶段并发**：落盘和核验是网络与磁盘等待，改成 4 路并发；计划顺序仍按你选择的行。
- **提交阶段去重**：每个插件的依赖图遍历从 3 次减到 1 次（真正派发前那次），锁探针从 2 次减到 1 次（同样在派发前）。
- **记录实际用时**：每个插件记 `ms`，整批记 `timings.prepareMs` / `commitMs` / `totalMs`，面板结果表的状态列下面直接显示该行用了多久。

## 为什么确认之后还是慢

这个要说实话：**每个插件的主要时间不在我们这边，而在官方管理器的「移除 → 装回 → 重新加载」**。你那批 5 个插件的记录显示，每个约 12–27 秒，其中 pnpm 只占 1.2–2.5 秒，剩下的是宿主自己卸载旧插件、写 profile、装新包、重建客户端模块并等待新实例 active。

这一段我们没法并行，也不能替宿主跳过：profile 只有一把写锁，两个安装不能同时进行；跳过移除又会留下旧代际。

本版能做的，是把自己那部分从每个插件约 3–5 秒压到 1–2 秒，并把耗时如实显示出来，不再让「慢」没有出处。

## 验证

- 回归 449 项通过。
- 口径没变：仍然只走公开源、暂存字节核验、装后核对实际文件与 Host 行、失败回滚。

## 限制

- 没有在你的机器上重跑一次真实批次来对比耗时；上面的数字来自你的历史记录与本机离线测量。真实收益要等下一次批量更新才看得到。
- 面板只能在整批结束后显示逐项用时，运行中仍显示步骤名。
