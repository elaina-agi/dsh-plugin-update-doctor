# Controlled ESM export-change comparison

## Scope

This experiment compares actual installed DSH **0.2.2-rc.3** AppBoot, Cordis, Loader, HMR and PluginManager in **separate fresh processes and unique temporary profiles**. It does not install plugins into the user's profile or operate the current GUI.

Generated package `module-cache-proof-plugin`:

- **1.0.0:** `helper.js` exports `legacyValue`, but **does not export `newValue`**. The entry imports/calls `legacyValue`.
- **1.1.0:** `helper.js` adds `newValue`; the new entry imports/calls that named export. Its real service returns `new-export-1.1.0`.
- **1.2.0:** a separate deliberately throwing activation fixture for explicit recovery checks. Its failure is **not an ESM-cache reproduction** and must not be presented as one.

The generated package has no dependency, native component, install script, core-service override, preset or Client half. This controlled helper-import change is simpler than WSL's module/preset/resource graph.

## Routes under comparison

1. **Official:** `PluginManager.updateBundle(name, '1.1.0', {registry})`, including its actual remove/install implementation.
2. **Generic updater:** production `DoctorService.runBatch()` invokes actual `manager.removeBundle()` and `manager.installBundle()` on verified local fixture archives. It does **not** use the WSL generation adapter.
3. **Cold 1.1.0:** a fresh process/profile starts directly on the new version, proving the package with the added export is valid independently of hot replacement.

Both update routes record package outcomes, real code return values, target active rows, same-process identity, disposal/start order, unrelated-service availability, any real update error/restoration, and separate intentional activation-failure recovery.

## Final evidence

**Historical evidence, not a current v0.3.0 rerun:** the generic runner's internal record predates the source-bound plan/reference requirements. Its generic mode needs adaptation before it can be used as a current integration test. The observed historical outcomes below are preserved, not reclassified as new failures or fixes.

See ignored local `module-cache-proof-result.json`, generated by `run-module-cache-proof.ps1`. Raw evidence includes local temporary paths and must not be distributed unredacted.

Final verified run:

| Route | Management result | Actual code | Target rows | Recovery control |
|---|---|---|---|---|
| Official `updateBundle` | `applied`, no warnings | `new-export-1.1.0` | 1/1 active, same isolated process | explicit old reinstall returned `helper-v1`, active |
| Production generic `runBatch` | `applied`, no warnings | `new-export-1.1.0` | 1/1 active, same isolated process | explicit old reinstall returned `helper-v1`, active |
| Cold new-version control | cold loaded 1.1.0 | `new-export-1.1.0` | 1/1 active in a separate process | not applicable |

Both update routes stopped/disposed the old fixture before starting the new one; the unrelated service remained callable. **No stale-ESM/missing-export error was reproduced. Both routes succeeded.** This does not demonstrate an advantage for the generic updater over the official path.

The independently bad 1.2.0 fixture correctly reported its intentional activation error despite package exit code 0. Actual `removeBundle` / `installBundle` then restored 1.0.0 code and active state in each original process. This separate control is not presented as a cache failure or an automatic production rollback proof.

All three final children used package copies from a store and cache beneath their own temporary roots. Actual pnpm output and parsed `.modules.yaml` `storeDir` were checked. Their ephemeral registry listeners and temporary roots were closed/deleted after absolute non-symlink path verification.

Earlier exploratory runs revealed pnpm 11 ignores these store settings in `.npmrc`, so they initially used the normal package-manager store. The final runner moves settings to `pnpm-workspace.yaml` and verifies actual use. One intermediate runner assertion failed because it searched escaped YAML text instead of parsing it; that was a test-harness failure before Host update, not a package/cache failure. All its owned roots were cleaned. Final successful evidence supersedes those exploratory runs without rewriting them as cache failures.

The controlled added-export transition **does not by itself establish a stale-module failure**. Success here is an ordinary update control, not proof that the updater repairs a generic official failure.

## Real implementation versus fixtures

- **Real:** installed AppBoot/Cordis/Loader/HMR/PluginManager, package operations, SHA512 and TAR/patch checks from production `RegistryStager`, native read-only `probeLocks`, production `DoctorService.runBatch`, installed entry/helper execution, and explicit recovery package operations.
- **Fixture:** generated package and owned loopback npm registry; HTTPS logical staging URL is mapped to that loopback fixture through an injected fetch adapter. The adapter changes transport only and does not replace archive verification or update results.
- **Fixture:** readiness callback and empty Agent registry for production `TaskGate`; there is no task or model request. This does not prove real Agent cancellation, task continuity or browser synchronization.
- The test directly drives `runBatch()` only for its own generated fixture, without obtaining a real user's confirmation ticket. It does not test the panel's authentication or user interaction.
- A `runBatch` record currently labels staged origin `https://registry.npmjs.org` unconditionally. In this experiment the bytes are **owned fixture bytes**, not public npm releases; the test does not treat that label as provenance evidence.
- Intentional bad activation is exercised through real manager calls and explicit reinstall of old bytes. It is not evidence of automatic production-batch rollback for a genuine cache failure.

## Cleanup and execution

Each child binds its registry only to `127.0.0.1` on a unique ephemeral port. It closes the listener and Host, checks the owned root's resolved absolute path and non-symlink directory identity, then deletes only its `mkdtemp` root. Wrapper timeout is 240 seconds per child; only the process tree it created may be terminated. Normal runs persist evidence after cleanup.

```powershell
.\experiments\run-module-cache-proof.ps1
```

No production files, user profile, WSL package, current GUI or user tasks are changed. The raw result filename is already covered by `experiments/*-result.json` ignore policy. No commit is made by this experiment.
